Scripting the client

Scripting is a supported feature of this client, not something tolerated. Between 2004 and 2010 people wrote thousands of scripts for the bots of the day, and those bots each had their own API. This client runs scripts written for four of them, from the same folder, under the same commands — plus a fifth flavour, calculators, for skill planning rather than playing.

TierFileLooks likeGuide
STS (the native tier)Name.java extends Methods, you write MainBody() and own the loop sts.html
TextScriptName.txt [label] blocks, one command per line, no Java at all textscript.html
APOSName.java extends Script, you write init()/main()/paint() and the client owns the loop apos.html
SBoTName.java extends Script, declares chat commands it answers to sbot.html
CalculatorsName.java extends Calculator, declares inputs, computes an answer — never touches the world calculators.html

Which one should I write?

New scripts: write STS or TextScript. STS is the native tier — the richest API (260-plus methods), interactive option menus, events, an on-screen overlay. TextScript is the no-programming tier: if you can write a shopping list you can automate mining. APOS and SBoT exist so that scripts people still have on disk run untouched; they are complete and maintained, but there is no reason to start a new script against a compatibility surface.

Running a script

Drop the file into the right folder beside the jar and it appears — no build step, no forking the client:

scripts/STS/Miner.java        the STS tier
scripts/Textscript/Coal.txt   TextScript
scripts/APOS/Fisher.java      APOS
scripts/SBoT/Test.java        SBoT
calculators/MaxHit.java       calculators

In game:

F2 (or /menu)the script menu — pick a script, pick a calculator, settings, recorder
/start Name(arg,arg)start a script by name — /start Miner(coal). Both argument shapes work: /start Miner coal too
/stopstop the running script
/reloadrecompile and restart after you edit the file
/scriptslist everything the client can see (also /macros, the STS name)
/debugtoggle script debug output
The / plane is yours. A chat line starting with / belongs to the client and is never sent to the server — recognised or not. An unrecognised / line is offered to the running script's input hook first, so scripts can take their own commands while running.

How loading works (all tiers)

  • The client compiles your source when you start it. If you run the client on a full JDK (the normal case — the launchers explain how to get one), a .java script is compiled in-process the moment you pick it. On a plain JRE, an already-compiled .class of the same name in the sibling script-bin/ (or calculators-bin/) folder is used instead.
  • No package line, no imports. Script sources are staged with import org.rscdaemon.client.*; prepended. That one line is the whole compatibility layer — your file starts straight at public class.
  • Name collisions resolve to Java. A Name.java wins over a Name.txt of the same name.
  • Java tiers are told apart by their constructor. A compiled script whose constructor takes mudclient is STS (or SBoT, by its folder); one whose constructor takes Extension is APOS. That is the only distinction the loader needs.

Where these came from

The lineage is documented, not folklore. SBoT was RichyT's bot; STS (SkullTorchaScriptable) is the API this client implements natively, recovered from the STS203C release, which also shipped Reines's SBoT emulator — the mapping this client's SBoT tier preserves. TextScript v1.6 was itself an STS script that interpreted .txt files, re-implemented here natively; its 131-command set was recovered from the original's own string table. APOS is a separate, later bot with an unrelated API, reimplemented from its javadoc and the sixteen surviving scripts. The full history, including what could not be honoured and why, is in CLIENT.md.

One warning, seriously meant: never run a pre-built client jar you did not build. The scripting lineage this client inherits from once shipped a jar with credential-stealing code in it. Build from source you can read — that is why the source is open.
